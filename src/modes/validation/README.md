# `src/modes/validation`

Validation mode: an inbound `Authorization: Bearer <token>` is checked against the provider's RFC 7662 introspection endpoint and the request is forwarded or refused. The wire behaviour and the credential choice are in the root README under [Validation mode](../../../README.md#validation-mode-authmode--validation) and [Introspection client identity](../../../README.md#introspection-client-identity); revocation under [Revocation and the access-token lifetime](../../../README.md#revocation-and-the-access-token-lifetime). This file states who owns what and which test pins it. The boundary review behind it is [#95](https://github.com/o3co/auth.proxy/issues/95).

## Responsibility

| File | Kind | Owns |
| --- | --- | --- |
| [`introspection-client.mts`](introspection-client.mts) | external connection behind [`IntrospectionClient`](introspection-client.mts) | one `POST` per call and the response read as RFC 7662 — the status, the body as a JSON object read at most [`MAX_INTROSPECTION_BODY_BYTES`](introspection-client.mts) of (64 KiB, #95 F39), `active` being a boolean; the error contract [`IntrospectHttpError`](introspection-client.mts), the result type [`IntrospectionResult`](introspection-client.mts), the credential choice [`buildAuthHeader`](introspection-client.mts). No state. |
| [`introspection-cache.mts`](introspection-cache.mts) | interface + in-memory implementation | [`IntrospectionCache`](introspection-cache.mts) entries: served while live, swept on write, bounded at `maxEntries`. Keyed by whatever the caller keys it by. |
| [`introspect.mts`](introspect.mts) | process | what this path accepts on top of a valid response and what may be cached ([`createIntrospector`](introspect.mts)): the Bearer-only refusals, the malformed-`exp` 502, the token that expired during the call, the digest key, the bound anchored at the request, and the one flight the digest also keys (#95 F6). Returns the [`Introspector`](decision.mts) the decision reads. No state of its own. |
| [`decision.mts`](decision.mts) | process | the validation decision ([`decideValidation`](decision.mts)): two header values in, a [`ValidationOutcome`](decision.mts) out — `forward` or `reject` (status, the `{ code, message }` body and the challenge, if there is one); what it needs is [`ValidationDeps`](decision.mts), an [`Introspector`](decision.mts) and the logger. No state of its own. |
| [`router.mts`](router.mts) | assembly + transport | [`createRouter`](router.mts) builds the client, the cache and the introspector between them ([`buildIntrospector`](router.mts)) — or takes `deps.introspect` and `deps.logger` — and mounts the shared upstream stage ([`createUpstreamProxy`](../../router/upstream.mts)); [`validationMiddleware`](router.mts) reads the two headers, calls `decideValidation` and applies the outcome to `req` / `res`, throwing on an outcome kind it does not know (the `never` guard). |

The three replaceable pieces the injection path already had are here now (#95 F5): the provider's endpoint behind [`IntrospectionClient`](introspection-client.mts), the store behind [`IntrospectionCache`](introspection-cache.mts), and between them the reading of the response that decides what may be held. The cache belongs to the router that built it rather than to the module, so two routers in one process no longer share one — [`app.mts`](../../app.mts) builds a single router, and the injection path draws the same line. The decision reads an [`Introspector`](decision.mts), a function `(token, requestId) → IntrospectionResult`, which [`buildIntrospector`](router.mts) composes from the three; a caller may supply its own through `deps` (#95 F3), and then owns everything below that seam.

## Public contract

`createRouter({ config, deps? })` returns an Express router and throws unless `auth.mode` is `"validation"` (the guard at the top of [`createRouter`](router.mts)); `deps` may supply the introspector and the logger, defaulting to what it builds — pinned by [`accepts an injected introspector and logger: fetch and the singleton are not touched, and the inbound bytes are forwarded`](__tests__/router.test.mts) and [`an injected logger receives the introspect failure line`](__tests__/router.test.mts). Refusals are `{ "code", "message" }` — a different shape from injection's — and exactly one of them carries a `WWW-Authenticate` challenge (#95 F29): the 401, as `Bearer error="invalid_token"`. RFC 6750 §3 makes the header a MUST on a refusal and a SHOULD to name the `error` **when the request included an access token**, and only the 401 meets that second condition. The 400 does not — §3.1's last paragraph keeps an error code off a request that "attempted using an unsupported authentication method", and the `Bearer realm="…"` the RFC offers instead needs a name nothing configures (F45 on #95). The 500 and the 502 are the proxy's or the provider's failure rather than a statement about the credential. No `realm` and no `error_description` on the one challenge there is: `realm` is OPTIONAL with no configured name, and the body already carries the wording. Pinned by the [`the RFC 6750 challenge`](__tests__/decision.test.mts) block and, on the wire, by the four router cases below. Injection mode answers no challenge at all, deliberately — see [`src/modes/injection`](../injection/README.md).

| Inbound | Answer | Where | Pinned by ([`router.test.mts`](__tests__/router.test.mts)) |
| --- | --- | --- | --- |
| no `Authorization` | forwarded unchanged | the first check in [`decideValidation`](decision.mts) | `passes a request without Authorization through to upstream without consulting the provider` |
| not `Bearer <token>` (scheme case-sensitive) | `400 Invalid Token Type`, no challenge | `extractBearerToken` returning `null` | `answers 400 Invalid Token Type to a non-Bearer scheme without consulting the provider` |
| anything but `active: true` — `false`, including a `cnf`, a non-Bearer `token_type` or expiry during the call, and any non-boolean a supplied introspector returns | `401 Invalid Token` + `WWW-Authenticate: Bearer error="invalid_token"` | the `result.active !== true` check in `decideValidation` | `refuses bound token %j before forwarding`; `forwards a live token, then refuses it when its warm cache reaches exp` |
| provider `401`, no client credentials | `401 Invalid Token` + the same challenge | `IntrospectHttpError` carrying `refusedCredential: "token"` in the `catch` | `answers 401 Invalid Token when the provider answers 401` |
| provider `401`, client credentials configured | `502 Provider Configuration Error` | the same error carrying `refusedCredential: "client"` (F7) | `answers 502 Provider Configuration Error to a provider 401 when client credentials are configured` |
| provider `3xx` | `502 Provider Configuration Error` | the client sets `redirect: "manual"`, so the redirect arrives as an `IntrospectHttpError` with its own status (F43) | `answers 502 Provider Configuration Error when the introspection endpoint redirects` |
| any other failure: non-2xx, invalid body, timeout, network | `500 Internal Server Error` | the `catch` fallthrough | `answers 500 Internal Server Error when $failure` (a provider 503, a 200 with a non-JSON body, a rejected `fetch`) |
| `active: true` | forwarded; upstream receives the inbound `Authorization` bytes | `forward`, applied as `next()` into the shared stage ([`createUpstreamProxy`](../../router/upstream.mts)) | `forwards a live token, then refuses it when its warm cache reaches exp`; the bytes: `accepts an injected introspector and logger: fetch and the singleton are not touched, and the inbound bytes are forwarded` |

**What a provider 401 means (F7).** RFC 7662 §2.3 has the introspection request authenticated, so the provider's `401` answers whichever credential it carried — and [`createIntrospectionClient`](introspection-client.mts) is the only thing that knows which. Without client credentials the inbound token *is* that credential (`Bearer <token>`, [`buildAuthHeader`](introspection-client.mts)), the 401 is about the caller, and `401 Invalid Token` is right. With `CLIENT_ID` / `CLIENT_SECRET` the credential is the proxy's own `client_secret_basic`: the 401 refused the proxy, the caller's token was never examined, and answering `401 Invalid Token` told the caller their token was bad when the deployment was misconfigured. The client marks which one on the error ([`RefusedCredential`](introspection-client.mts)) and the decision answers `502 Provider Configuration Error` for `client`, logged as `introspect refused the proxy's client credentials` rather than the generic `introspect failed`. Injection mode tells the two apart too (`provider_config_error` 502): the exchange always has, and the session grant since #95 F47. A supplied introspector that marks nothing is read as it always was: any 401 it raises is `401 Invalid Token`.

## Inputs and outputs

- In: `Authorization`, read by [`extractBearerToken`](../../express/bearer.mts) — case-sensitive `Bearer`, then the first SP-delimited word; `x-request-id` as normalised by [`express/requestId.mts`](../../express/README.md).
- Out, provider: `POST auth.validation.introspect.url` — never followed if it redirects (`redirect: "manual"`, #95 F43; a same-origin 307/308 would re-send this request's credential to a path nothing configured) — form body `token=<token>`, `Authorization` either Basic (both client credentials set) or `Bearer <token>`, `x-request-id` — the **leader's**, when concurrent requests coalesce (invariant 7) — `AbortSignal.timeout(timeoutMs)` (the `fetch` call in [`createIntrospectionClient`](introspection-client.mts)).
- Out, upstream: the inbound request with every inbound header — `express-http-proxy` copies `req.headers` wholesale except `connection` and `host`, cookies included (`reqHeaders` in its `lib/requestOptions.js`); this middleware modifies nothing, and the shared stage's decorator only re-sets casing ([`createUpstreamProxy`](../../router/upstream.mts)). **The forwarded header is the inbound bytes unchanged, while the introspected token is the first SP-delimited word** (F14): `Bearer abc123 extra` introspects `abc123` and forwards `Bearer abc123 extra`. The extraction half is pinned by [`keeps only the first token when the header carries trailing content`](../../express/__tests__/bearer.test.mts) and [`forwards an active token, handing the introspector the first SP-delimited word and the request id`](__tests__/decision.test.mts); the forwarding half by [`accepts an injected introspector and logger: fetch and the singleton are not touched, and the inbound bytes are forwarded`](__tests__/router.test.mts). The upstream must verify the token it is handed regardless ([Inbound Authorization headers](../../../README.md#inbound-authorization-headers)).

## Invariants

1. **Parsed once.** `Authorization` is parsed once, by [`extractBearerToken`](../../express/bearer.mts) at the top of [`decideValidation`](decision.mts), and every later step reads the `token` it answered. What is forwarded is decided by `req.headers`, which the middleware never modifies on this path: the library copies every inbound header and the shared stage's decorator only re-sets casing — see the docstring on [`createUpstreamProxy`](../../router/upstream.mts), which also notes that dropping the decorator is tracked with F14 on #95. The parsed header carries the token alone since F15, and is the token itself since #95 F36; the header as received was never read, because what goes upstream is `req.headers`.
2. **Cache key and bound.** Key = SHA-256 of the token (`cacheKey` in [`introspect.mts`](introspect.mts)). An entry expires at `min(now + cacheTtlSec, exp)` with `now` captured before the call, so entries are capped at `exp` and anchored at the request. Pinned by [`returns the cached result on a second call within the TTL, calling the provider once`](__tests__/introspect.test.mts), [`keys the entry by the digest of the token, never the token`](__tests__/introspect.test.mts), [`anchors the bound at the request, not at the response`](__tests__/introspect.test.mts), [`stops serving a warm entry at the token's exp`](__tests__/introspect.test.mts) and, through the router, [`forwards a live token, then refuses it when its warm cache reaches exp`](__tests__/router.test.mts). `cacheTtlSec` ≤ 0 disables both sides — [`neither reads nor writes the cache when caching is disabled`](__tests__/introspect.test.mts) — but not the flight (invariant 7).
3. **What is never cached:** a response carrying `cnf` or a non-Bearer `token_type` (answered `active: false`), a token that expired during the call, an entry already past its bound on arrival, and every error — each returns or throws before the single `cache.set` in [`createIntrospector`](introspect.mts). Pinned by [`refuses a positive response that expired during the provider call, and caches nothing`](__tests__/introspect.test.mts), [`refuses unsupported possession evidence on the Bearer path: %j`](__tests__/introspect.test.mts) (which asserts the empty cache), [`refuses bound token %j before forwarding`](__tests__/router.test.mts); the error case is documented, not tested.
4. **What is cached:** the validated response as returned, whether `active` is `true` or `false` — a plain `active: false` from the provider is a statement about the token and is held for the same bound, pinned by [`caches a plain active: false, which is the provider's answer about the token`](__tests__/introspect.test.mts). The refusals this path makes itself are not: they are not the provider's answer.
5. **Only a boolean `active` is trusted** (the RFC 7662 §2.2 check in [`createIntrospectionClient`](introspection-client.mts)); `{"active":"false"}` is a 502, not a bypass. Pinned by [`throws IntrospectHttpError(502) when active is not a boolean — %s`](__tests__/introspection-client.test.mts), [`throws IntrospectHttpError(502) when 200 body is valid JSON but not a plain object — %s`](__tests__/introspection-client.test.mts). The decision applies the same rule again on the value it is handed, since a supplied introspector owns that check (below).
6. **Eviction:** expired entries are swept, then the oldest insertion is dropped at `maxEntries` — both inside [`createIntrospectionCache`](introspection-cache.mts), which is the only thing that knows the bound. A write for a key the map already holds evicts nothing, since it cannot push the map past that bound — a deliberate difference from the function this replaced, which dropped a live entry for it. It used to be reachable through invariant 7 — two concurrent misses on one token both wrote, and the second was that duplicate — and since F6 it is not: one flight means one write ([`evicts once for a token two concurrent requests ask about (#95 F5, F6)`](__tests__/introspect.test.mts)). Pinned by [`evicts nothing when the write is a key it already holds, even at the bound`](__tests__/introspection-cache.test.mts), [`sweeps expired entries on the next write, so a stale one does not hold a slot`](__tests__/introspection-cache.test.mts), [`drops the oldest insertion at the bound`](__tests__/introspection-cache.test.mts) and, through the composition, [`evicts the oldest entry at maxEntries, so the evicted token is fetched again`](__tests__/introspect.test.mts).
7. **One flight per token (#95 F6).** Concurrent misses on one token share one provider call: the leader asks, the waiters are answered by its response — including the bound it anchored — and only the leader writes. The leader's rejection is every waiter's, and the slot clears in `finally` either way, so the next miss asks again. The table is [`SingleFlight`](../../single-flight.mts), the same one the session and exchange paths use, keyed by the same digest as the cache. It belongs to the router, like the cache, and a caller supplying `deps.introspect` gets neither and owns its own coalescing. The flight is independent of `cacheTtlSec`: setting it to `0` turns the cache off on both sides and still coalesces, so an operator asking for a fresh provider check per request gets one per *concurrent group* — [`coalesces concurrent misses even with the cache disabled`](__tests__/introspect.test.mts). Two consequences of sharing a call, neither of which the injection path signals here: the provider sees the **leader's** `x-request-id` and no other, so a waiter's refusal cannot be traced to a provider-side line; and a shared rejection is logged once per waiter, so the `introspect failed` rate counts requests rather than provider calls. The table is not bounded by `cacheMaxEntries` — its high-water mark is the number of distinct tokens in flight at once, bounded by `timeoutMs` and inbound concurrency. Pinned by [`calls the provider once for concurrent misses on one token, and answers both`](__tests__/introspect.test.mts), [`does not coalesce two different tokens`](__tests__/introspect.test.mts), [`shares a rejection with every waiter without a second provider call`](__tests__/introspect.test.mts), [`releases the key, so the next miss calls the provider again`](__tests__/introspect.test.mts) and [`gives each router its own flight table, and neither when the introspector is supplied`](__tests__/build-introspector.test.mts).

## Failure and lifecycle

- [`IntrospectHttpError`](introspection-client.mts) carries the provider's status for a non-2xx and `502` for a 200 whose body is not a valid RFC 7662 response. **A 200 body is read at most [`MAX_INTROSPECTION_BODY_BYTES`](introspection-client.mts) of** (#95 F39), through the same [`readBoundedJsonObject`](../../response-body.mts) the injection clients use: a body over the bound, or one that is not a JSON object, is a `502` and the stream is cancelled at the bound rather than drained. Until F39 this path buffered whatever arrived, once per request in flight — the one unbounded read left after F35 bounded the injection side. 64 KiB is the token response's allowance too: an introspection response is a claim set and can be generous, and nothing a provider legitimately sends comes near it. The decode is UTF-8 with a leading BOM dropped, which is what `resp.json()` did. Pinned by the [`the bound on a 200 body`](__tests__/introspection-client.test.mts) block — the exact boundary, the stream stopped at it, a 32 KiB claim set admitted, a BOM read. The non-2xx body is cancelled before the throw (#95 F28), through [`discardBody`](../../response-body.mts), which the injection clients use for the same reason (F37): nothing on this path reads an error body. An unread one beyond undici's 64 KiB read-ahead holds its socket until the response is collected; within it — every realistic refusal body — undici has already pooled the socket, so this is defensive — [`cancels the body of a %d response instead of leaving it unread`](__tests__/introspection-client.test.mts). A cancel that itself fails is swallowed, so the status survives it — [`keeps the provider's status when cancelling the body fails`](__tests__/introspection-client.test.mts). Every other refusal runs after [`readBoundedJsonObject`](../../response-body.mts) has either read the body to its end or cancelled it at the bound. A rejected `fetch` — timeout or network — propagates unwrapped ([`propagates fetch rejection (network error / AbortError)`](__tests__/introspection-client.test.mts)); the decision logs `introspect failed` with the error under `x-request-id` and answers 500. Two statuses come out of that `catch` instead: a 401 whose `refusedCredential` is `token` — or that carries no mark, which is how a supplied introspector's 401 is read — is `401 Invalid Token`, and a 401 marked `client` is `502 Provider Configuration Error` under its own log line, `introspect refused the proxy's client credentials` (F7). ([`answers 500 Internal Server Error when $failure`](__tests__/router.test.mts), [`answers 401 Invalid Token when the provider answers 401, logging the failure with the request id`](__tests__/decision.test.mts), [`answers 502 when the provider refused the proxy's own client credentials`](__tests__/decision.test.mts).)
- **A supplied introspector owns what `introspect` guarantees:** the RFC 7662 boolean `active` check — the decision forwards on `true` alone, so a non-boolean is `401 Invalid Token`, never a bypass ([`answers 401 Invalid Token when a supplied introspector resolves a non-boolean active (%j), never forwarding on truthiness`](__tests__/decision.test.mts)) — the `cnf` / `token_type` / expiry refusals, and its own timeout; the decision applies none of them. What `createRouter` builds is the bundled implementation of exactly that contract, and a caller replacing it replaces the client, the cache and the reading between them together — [`does not build either when the caller supplies its own introspector`](__tests__/build-introspector.test.mts).
- **Cancellation is the timeout only (#95 F10).** Neither [`IntrospectionClient`](introspection-client.mts) nor [`Introspector`](decision.mts) accepts a signal, and the sole abort is `AbortSignal.timeout(timeoutMs)` in [`createIntrospectionClient`](introspection-client.mts). A caller that disconnects does not abort the provider call, and with invariant 7 that matters: the disconnecting caller may be the *leader* of a flight others are waiting on, so honouring its signal would fail requests that are still there. The flight completes and serves its waiters. The entry is written only when caching is on and the response is cacheable — `cacheTtlSec` ≤ 0 writes nothing (invariant 2), and a refusal this path makes itself is never cached (invariant 3) — and only then is the next request served from it. Pinned, for the cached case, by [`a disconnect does not abort the flight its waiters share, and the answer is still cached`](__tests__/router.test.mts), which destroys the leader's socket mid-flight. Adding a signal would mean aborting only when every waiter has gone, which is refcounting a flight for a call the configured `timeoutMs` already bounds — a bound the operator sets and nothing caps, so a long timeout is a long-lived abandoned flight, whose result the next request still gets from the cache. The timeout stays the only cancellation.
- **Lifetime (F21):** the cache and the flight table are created by [`createRouter`](router.mts) and live in its closure until process exit — one of each per router, pinned by [`gives each router its own cache, so one router's entries are not another's`](__tests__/build-introspector.test.mts) and [`gives each router its own flight table, and neither when the introspector is supplied`](__tests__/build-introspector.test.mts); [`app.mts`](../../app.mts) builds one router and passes no `cleanup`, so a drain does not wipe it. [`IntrospectionCache.clear()`](introspection-cache.mts) is unreachable from outside for a router-built instance; a caller that supplies `deps.introspect` owns whatever it built. Nothing the router builds needs releasing.
- `cacheMaxEntries` and `timeoutMs` no longer carry a third declaration: the parameter defaults went with the fused function (F23), and the schema is the only place they are declared — see [`config/README.md`](../../../config/README.md).
