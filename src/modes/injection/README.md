# `src/modes/injection`

Injection mode: a session cookie — or, with the exchange enabled, an external JWT — becomes the outbound `Authorization: Bearer` header. The wire behaviour is in the root README under [Injection mode](../../../README.md#injection-mode-authmode--injection), [Cache behavior](../../../README.md#cache-behavior), [Scope boundary](../../../README.md#scope-boundary), [CSRF responsibility boundary](../../../README.md#csrf-responsibility-boundary), [Cookie forwarding](../../../README.md#cookie-forwarding) and [External credential exchange](../../../README.md#external-credential-exchange-authinjectionexchange). This file states who owns which decision and which state, and which test pins each invariant. The boundary review behind it is [#95](https://github.com/o3co/auth.proxy/issues/95).

The pre-existing exchange-path tests still replace the provider by stubbing global `fetch`, which is what exercises the real jwt-bearer client.

## Public contract

`createRouter({ config, deps? })` returns an Express router and throws unless `auth.mode` is `"injection"` (the guard at the top of [`createRouter`](router.mts)). Every refusal is `{ "error", "error_description" }` with no `WWW-Authenticate` — the body is the contract here, and the caller of an injection-mode proxy holds a session cookie rather than a Bearer token, so there is no RFC 6750 credential to challenge for; validation mode carries one on its 401 (#95 F29) — and the provider's `Retry-After` passed through (the `respond` outcome of [`decideInjection`](decision.mts) as applied by [`injectionMiddleware`](router.mts); [`respond`](exchange.mts) on the exchange path). The `error` values are the two error-code types linked above, plus the refusals [`decideExchange`](exchange.mts) emits before any provider call, listed in its doc comment — `credential_ambiguous` (400), `credential_unsupported` (401), and, when `allowedIssuers` is configured, `credential_rejected` (401) for an assertion whose `iss` is outside it — except that `session_unauthorized` is answered as `session_required` (the body built in the `catch` of [`decideInjection`](decision.mts)); an unclassified throw is `502 provider_unavailable` (the fallthrough of each `catch`, in [`decideInjection`](decision.mts) and [`decideExchange`](exchange.mts)).

## Inputs and outputs

- In: the one `Cookie` pair named `auth.injection.sessionCookieName`; `Authorization` (presence only on the session path, parsed on the exchange path); `x-request-id` as normalised by [`express/requestId.mts`](../../express/README.md).
- Out, provider: `POST {providerOrigin}/oauth/token` with `grant_type=session` as a public client — `client_id` in the body, only the session cookie forwarded, no `Authorization` ([`createSessionGrantClient`](session-grant-client.mts)) — or `grant_type=jwt-bearer` with `client_secret_basic` ([`createJwtBearerClient`](jwt-bearer-client.mts), see [`src/oauth`](../../oauth/README.md)).
- Out, upstream: the inbound request with every inbound header — `express-http-proxy` copies `req.headers` wholesale except `connection` and `host`, cookies included (`reqHeaders` in its `lib/requestOptions.js`), and the shared stage's decorator only re-sets casing ([`createUpstreamProxy`](../../router/upstream.mts)). `Authorization` is therefore whatever `req.headers` holds when the stage runs: set to the minted token (the `inject` outcome), deleted (the `forward_stripped` outcome, when `stripInboundAuthorization` is on), or left as received (`forward`). The strip works because [`injectionMiddleware`](router.mts) applies the outcome on `req.headers` before the stage — see its doc comment; why the strip is opt-in is the comment above [`forwardWithoutInjection`](decision.mts).
- Logs: the per-request `incoming request` line (`x-request-id`, `method`, `path`; no `event` key) and `injection.*` events carrying the request id and bounded classes only (see [Invariants](#invariants)). On the two lines that report a forward without injection — `injection.no_cookie` and `injection.cookie_rejected` — `action` is the outcome's own kind, `forward` or `forward_stripped`, read from the one predicate that decides it (#95 F31); `fallback` on `injection.cookie_rejected` is the third case, where a malformed pair was skipped and the request goes on to attempt the mint.

Outside the directory: [`express/requestId`](../../express/requestId.mts), [`router/upstream`](../../router/upstream.mts), the [`logger`](../../logger.mts) singleton (`router` uses it as the default `deps.logger`; `decision` and `exchange` only see the [`Logger`](../../logger.mts) type), and the config types. No cycles, and no client depends on another: the two helpers they shared live in `token-endpoint.mts` since F19, beside `provider-error.mts`, which plays the same part for error bodies.

## Invariants

1. **Parsed once.** `req.headers.cookie` is parsed once, at the top of [`decideInjection`](decision.mts); every later step reads `extraction.kind` / `.value` / `.skipped`. On the exchange path `Authorization` is handed over once and parsed once, by [`parseBearerAssertion`](bearer-assertion.mts) at the top of [`decideExchange`](exchange.mts); later steps read `parsed.*`. The session path never parses `Authorization`: the exchange hand-off condition, [`forwardWithoutInjection`](decision.mts) and [`inject`](decision.mts) only check presence. The parsers are tested on their own; that each is called once per request is documented, not tested.
2. **Bytes are not logged; the bounded reason class is, and a provider's text only after sanitising** — [`CookieRejectReason`](cookie-extractor.mts), [`AssertionRejectReason`](bearer-assertion.mts), a provider `error` only after [`sanitizeErrorCode`](provider-error.mts), an `error_description` only after [`sanitizeErrorDescription`](provider-error.mts); the unverified `iss` is not logged (the `allowedIssuers` prefilter in [`decideExchange`](exchange.mts)). The one exception: an unclassified throw is logged as `error: String(err)` (`injection.unexpected_error`, `injection.exchange_unexpected_error`), whatever that error's message holds. Pinned by [`never carries the value bytes in the result`](__tests__/cookie-extractor.test.mts), [`neither logs nor returns a session cookie the provider echoes in error_description`](__tests__/router.test.mts), [`forwards a grammar-rejected session cookie anonymously and logs injection.cookie_rejected at warn (#23, #73)`](__tests__/router.test.mts), [`uses the first well-formed same-name pair and logs the skipped malformed one (#74)`](__tests__/router.test.mts), [`does not log a credential a provider echoes back as its error code`](__tests__/exchange-router.test.mts), [`never logs the assertion, the issued token or the client secret`](__tests__/exchange-router.test.mts), [`logs neither the assertion, the issued token, the issuer nor the client secret on any path`](__tests__/exchange-decision.test.mts), [`never puts the assertion or the client secret into an error message`](__tests__/jwt-bearer-client.test.mts), [`drops a provider error_description that is not a safe RFC 6749 description`](__tests__/session-grant-client.test.mts). There is no length threshold since #95 F30: the sanitisers redact a credential wherever it appears in a provider's text, at any length, and skip only an empty one. Below eight characters they used to require an exact echo, which let a session cookie value of `abc` reach a log line and a relayed `error_description` inside `bad abc` — and the proxy does not choose that value's length. The cost is that a very short credential refuses almost any text: what is lost is the provider's diagnostic, never the answer, since the callers classify the raw value before sanitising and substitute their own wording for a refusal. Pinned by [`refuses text containing a credential of %d characters, not only an exact echo`](__tests__/provider-error.test.mts), [`refuses ordinary text that happens to contain a very short credential`](__tests__/provider-error.test.mts), [`ignores an empty credential rather than refusing everything`](__tests__/provider-error.test.mts) and, where it is paid, [`drops a provider error_description that contains the session cookie value, however short`](__tests__/session-grant-client.test.mts).
3. **The cache is written only on success.** The only `set` calls sit inside the flight after the client returned — the grant fetcher in [`decideInjection`](decision.mts) and the exchange fetcher in [`decideExchange`](exchange.mts); no `catch` writes. A provider call happens only when `get` returned `null`, and [`TokenCache.get`](token-cache.mts) evicts an expired entry on read, so a provider error has no live entry to touch. Failures are not cached: [`does not cache a failure: the next identical request is submitted again`](__tests__/exchange-router.test.mts), [`never caches a failure: the next presentation is submitted again`](__tests__/exchange-decision.test.mts); on the session path: [`does not cache a failure: the next identical call reaches the client again`](__tests__/decision.test.mts).
4. **Expiry is anchored at the request instant.** `requestedAt` is captured before the call goes out (in both fetchers) and the entry expires at `min(requestedAt + ttl, requestedAt + expires_in, exp) − safetyMargin`, where `exp` is the assertion's absolute expiry and exists on the exchange path only (the session path passes no `notAfter`); the entry is not written when that instant is already past. Pinned by [`anchors ttl and expires_in at the request, not at the response`](__tests__/cache-expiry.test.mts), [`keeps an absolute notAfter where it is, however slow the response`](__tests__/cache-expiry.test.mts), [`returns null (do not cache) when the expiry is not after now`](__tests__/cache-expiry.test.mts), [`counts the grant's expires_in from the request, not from a slow response`](__tests__/router.test.mts), [`does not cache a grant whose response arrives after expires_in minus the margin`](__tests__/router.test.mts), [`counts expires_in from the request, not from a slow response`](__tests__/exchange-router.test.mts), [`does not cache at all when the response arrives after expires_in minus the margin`](__tests__/exchange-router.test.mts), [`never outlives the assertion's exp`](__tests__/exchange-router.test.mts), [`does not cache when the assertion has no exp`](__tests__/exchange-router.test.mts).
5. **One flight per key; the rejection is shared; the slot clears in `finally`** ([`SingleFlight.run`](../../single-flight.mts)). Keys: [`sessionCacheKey`](decision.mts) for the session path, [`exchangeCacheKey`](exchange.mts) for the exchange — each a SHA-256 over a JSON array of the grant context and the credential, so no field's text can shift into its neighbour's and neither credential leaves the digest. The exchange has its own cache and flight table (built by [`createRouter`](router.mts), or supplied under `deps.exchange`), so a cookie whose value equals an assertion never hits the other cache. Pinned by [`invokes fetcher once for concurrent run() on the same key`](../../__tests__/single-flight.test.mts), [`propagates rejection to all concurrent waiters on the same key`](../../__tests__/single-flight.test.mts), [`clears pending entry after success`](../../__tests__/single-flight.test.mts), [`clears pending entry after failure`](../../__tests__/single-flight.test.mts), [`coalesces concurrent requests with the same cookie into one provider call`](__tests__/router.test.mts), [`coalesces concurrent calls for the same cookie into one grant call and shares the token`](__tests__/decision.test.mts), [`shares a rejection with every concurrent waiter without a second grant call`](__tests__/decision.test.mts), [`submits an assertion once for concurrent identical requests`](__tests__/exchange-router.test.mts), [`shares a refusal with every concurrent identical request instead of resubmitting`](__tests__/exchange-router.test.mts), [`does not share entries with the session cache`](__tests__/exchange-router.test.mts), and the [`exchangeCacheKey` tests](__tests__/exchange.test.mts). Both keys carry their grant context — the exchange key since #90, the session key since #95 F33: the session key the grant type, provider, client, scope and cookie name; the exchange key the grant type, token endpoint, client, scope, audience and resource — so a supplied cache or flight table may now be shared between routers that differ in any of those: the second router asks the provider a different question and gets its own entry. What is still the caller's to match: the supplied `grantClient` / exchange `client`, which cannot be hashed; the exchange's `clientSecret`, which is not part of its context; and the cache policy (`ttlSeconds`, `safetyMarginSeconds`), which bounds how long an entry lives rather than which token comes back. One more consequence of sharing: a cookie now occupies one entry per grant context rather than one in total, against the same `maxEntries`, so a cache shared across N routers wants resizing. Pinned by the [`sessionCacheKey` tests](__tests__/decision.test.mts) and the [`exchangeCacheKey` tests](__tests__/exchange.test.mts).
6. **Cancellation is the timeout only.** Neither client accepts a signal; the sole abort is `AbortSignal.timeout(cfg.timeoutMs)` in [`createSessionGrantClient`](session-grant-client.mts) and [`createJwtBearerClient`](jwt-bearer-client.mts). A caller that disconnects does not abort a flight other waiters share: the flight completes and serves its waiters, and a successful grant is cached when it is cacheable — [`computeCacheExpiresAt`](cache-expiry.mts) refuses one whose bound has already passed, such as an `expires_in` inside the safety margin. (There is no disabled-cache case on this path: `tokenCache.ttlSeconds` is positive by schema.) Pinned on the session path by [`a disconnect does not abort the flight its waiters share, and the token is still cached`](__tests__/router.test.mts), which destroys the leader's socket mid-flight. The exchange path has the same mechanism and no disconnect test of its own; what is shared is [`SingleFlight`](../../single-flight.mts) and the absence of a signal parameter, not a second test. Taking a caller's signal was the alternative (#95 F10) and is not taken: honouring it would have to abort only when every waiter has gone, which is refcounting a flight for a call the configured `timeoutMs` already bounds — a bound nothing caps, so a long timeout is a long-lived abandoned flight, whose result the next request still gets from the cache.
7. **No retry, no fallback.** One submission per call (the doc comment on [`createJwtBearerClient`](jwt-bearer-client.mts)); the exchange never falls back to the session grant nor the reverse (the `credential_ambiguous` refusal in [`decideExchange`](exchange.mts); [`provider refusals — no pass-through, no session fallback`](__tests__/exchange-router.test.mts), [`rejects a session cookie together with an Authorization header (400), calling nothing`](__tests__/exchange-router.test.mts)). **Neither token client follows a redirect** (#95 F8): both set `redirect: "manual"` and answer `provider_config_error` 502 with `provider token endpoint redirected (<status>)` — [`createJwtBearerClient`](jwt-bearer-client.mts), which always did, and [`createSessionGrantClient`](session-grant-client.mts), which inherited `fetch`'s default of following up to twenty until F8. Pinned by [`does not follow redirects`](__tests__/jwt-bearer-client.test.mts) and [`maps a redirect to provider_config_error`](__tests__/jwt-bearer-client.test.mts) on one side, [`asks fetch not to follow a redirect`](__tests__/session-grant-client.test.mts) and [`refuses a 3xx rather than following it (%d)`](__tests__/session-grant-client.test.mts) on the other. The reason, measured on this Node rather than assumed, is that no way a followed redirect goes can be reported honestly, and it differs by status group. On a **307/308 same-origin** redirect the whole POST is replayed — session cookie and form body intact — to a path nothing configured, and it *succeeds*: a token minted from an endpoint the operator never named, with no line saying so. On a **307/308 cross-origin** one `fetch` strips the `Cookie`, so the provider sees an unauthenticated grant, answers 401, and the caller is told to authenticate again over an endpoint that is merely misconfigured. On a **301/302/303** the method becomes `GET` and the body is dropped, so a POST-only token endpoint answers 405 and the request was never a grant at all. Validation's [`createIntrospectionClient`](../validation/introspection-client.mts) still sets no `redirect` option — [`src/modes/validation`](../validation/README.md) owns that contract, and it is tracked separately on #95.

## Failure and lifecycle

- **Every response body is either read or released (#95 F37).** A branch that answers from the status alone — the session grant's 3xx, 5xx, unexpected 4xx and any 2xx other than 200, the exchange's 3xx — calls [`discardBody`](../../response-body.mts) before it throws; every other branch reads through `parseJsonBody` or `readBoundedJsonObject`, which drain or cancel. What that buys is bounded, and measured rather than assumed: a body within undici's 64 KiB read-ahead costs nothing either way, since undici has already read it and pooled the socket — and every realistic refusal body is that small. A larger unread body holds its socket until the response is collected; cancelling closes it instead, so held sockets cannot accumulate behind a provider sending large refusal bodies. A cancel that fails is swallowed so it cannot replace the refusal. Pinned by [`cancels the body of a %d it answers without reading (%s)`](__tests__/session-grant-client.test.mts), [`cancels the body of a redirect it refuses without reading`](__tests__/jwt-bearer-client.test.mts) and the two `keeps the refusal when cancelling the body fails` cases.
- **Timeout / network:** `provider_unavailable` 502 (the `fetch` `catch` in each client); [`throws provider_unavailable on timeout (AbortError)`](__tests__/session-grant-client.test.mts), [`maps a timeout to provider_unavailable`](__tests__/jwt-bearer-client.test.mts), [`answers 502 provider_unavailable on a network error or timeout`](__tests__/exchange-router.test.mts).
- **Provider answers:** the two error-code types say what each status and `error` becomes; the provider's own 401 is `provider_config_error` for the exchange ([`JwtBearerErrorCode`](jwt-bearer-client.mts)) and `session_unauthorized` for the session grant ([`SessionGrantErrorCode`](session-grant-client.mts)), because there the session cookie *is* the credential — unless its `error` is `invalid_client` (RFC 6749 §5.2), which means the proxy's own `clientId` was refused and is `provider_config_error` 502 like the exchange's (#95 F47). Telling those two apart is why the session 401 reads its body, bounded, where it used to discard it; a body past `MAX_ERROR_BODY_BYTES` is abandoned and read as the expired session it almost always is. Pinned by [`a 401 that refused the proxy's client`](__tests__/session-grant-client.test.mts) and, on the wire, [`returns 502 provider_config_error when the provider's 401 refused the proxy's client`](__tests__/router.test.mts). Both clients read only a `200` as success (RFC 6749 §5.1); any other 2xx is `provider_unavailable` 502, "unexpected provider response: <status>". The session grant took every 2xx until #95 F38 and refused a `204` as "provider returned 200 with a body that is not a JSON object" — a status the provider never sent, in the `error_description` the client reads. Pinned by [`refuses a %d carrying a token as an unexpected status`](__tests__/session-grant-client.test.mts) and [`refuses a %d as an unexpected status, not as a malformed 200`](__tests__/session-grant-client.test.mts). On the session path the **code alone** says what went wrong: [`SESSION_FAILURE_LINES`](decision.mts) maps it to the event and the level, and the same code decides the body's `error`. `status` decides only the status — the bundled client remaps a 400 `invalid_grant` to 401 deliberately, so the status is the client's to choose. Until #95 F32 the branch read the code for the body and the status for the log line. The bundled client pairs the two on every path, so nothing it throws is affected; a supplied [`grantClient`](decision.mts) need not, and it owns the pairing: an unpaired error is answered with its own status and its code's body, which a client keying off the status and one keying off the body will read differently. A code the union does not declare is logged as `injection.provider_unavailable`; a code added *to* the union fails the build at `SESSION_FAILURE_LINES` rather than arriving there. Pinned by [`a 401 that is not a session problem is not logged as one`](__tests__/decision.test.mts) and [`a session problem that is not a 401 is still logged as one`](__tests__/decision.test.mts). The exchange path has the same shape since #95 F41: [`EXCHANGE_FAILURE_LINES`](exchange.mts) maps each `JwtBearerErrorCode` to its level, event and message, and an undeclared code from a supplied client is logged as `injection.exchange_provider_unavailable` — it used to fall out of a `switch` with no default and leave no line at all, while the request was still answered. Pinned by [`logs a refusal whose code the union does not declare (%j), rather than nothing`](__tests__/exchange-decision.test.mts), which includes the prototype keys a plain-object lookup would mishandle.
- **State and lifetime (F21):** by default the session cache and flight table, and the exchange's, are built by [`createRouter`](router.mts) and live in its closure — created once per router, which [`app.mts`](../../app.mts) creates once, and held until process exit. There is no dispose for those: [`TokenCache.clear()` / `size()`](token-cache.mts) are unreachable from outside for the router-built instances, and [`app.mts`](../../app.mts) passes no `cleanup` to the shutdown, so a drain does not wipe the caches. When a caller supplies `deps.tokenCache` / `deps.singleFlight`, or `deps.exchange.tokenCache` / `deps.exchange.singleFlight` (#95 F2, F4), it owns them: they stay reachable to it, it may clear or dispose them, and it may share them between routers whose grant contexts differ, since #95 F33 put the context in the key — what it must still match is the supplied `grantClient` / exchange `client` and the cache policy, and their lifetime and cleanup are its responsibility — the router never clears what it did not build. Nothing needs releasing in the default construction — no timers, no held sockets; tokens die with the process ([Threat model — process memory](../../../README.md#threat-model--process-memory)). Documented, not tested.
