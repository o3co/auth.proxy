# `src/modes/injection`

Injection mode: a session cookie — or, with the exchange enabled, an external JWT — becomes the outbound `Authorization: Bearer` header. The wire behaviour is in the root README under [Injection mode](../../../README.md#injection-mode-authmode--injection), [Cache behavior](../../../README.md#cache-behavior), [Scope boundary](../../../README.md#scope-boundary), [CSRF responsibility boundary](../../../README.md#csrf-responsibility-boundary), [Cookie forwarding](../../../README.md#cookie-forwarding) and [External credential exchange](../../../README.md#external-credential-exchange-authinjectionexchange). This file states who owns which decision and which state, and which test pins each invariant. The boundary review behind it is [#95](https://github.com/o3co/auth.proxy/issues/95).

Today both decisions live inside Express handlers and `createRouter` hard-wires every implementation: [`Deps`](router.mts) is not exported, so tests replace the provider by stubbing global `fetch`, not by supplying a client. #95 tracks lifting the decisions out and making `deps` injectable; nothing below changes when that lands.

## Public contract

`createRouter({ config })` returns an Express router and throws unless `auth.mode` is `"injection"` (the guard at the top of [`createRouter`](router.mts)). Every refusal is `{ "error", "error_description" }` with no `WWW-Authenticate` and the provider's `Retry-After` passed through (the `catch` in [`injectionMiddleware`](router.mts), [`respond`](exchange.mts)). The `error` values are the two error-code types linked above, plus the two refusals [`createExchangeHandler`](exchange.mts) emits before any provider call — `credential_ambiguous` (400) and `credential_unsupported` (401), listed in its doc comment — except that `session_unauthorized` is answered as `session_required` (the body built in that `catch`); an unclassified throw is `502 provider_unavailable` (the fallthrough of each `catch`, in [`injectionMiddleware`](router.mts) and [`createExchangeHandler`](exchange.mts)).

## Inputs and outputs

- In: the one `Cookie` pair named `auth.injection.sessionCookieName`; `Authorization` (presence only on the session path, parsed on the exchange path); `x-request-id` as normalised by [`express/requestId.mts`](../../express/README.md).
- Out, provider: `POST {providerOrigin}/oauth/token` with `grant_type=session` as a public client — `client_id` in the body, only the session cookie forwarded, no `Authorization` ([`createSessionGrantClient`](session-grant-client.mts)) — or `grant_type=jwt-bearer` with `client_secret_basic` ([`createJwtBearerClient`](jwt-bearer-client.mts), see [`src/oauth`](../../oauth/README.md)).
- Out, upstream: the inbound request with every inbound header — `express-http-proxy` copies `req.headers` wholesale except `connection` and `host`, cookies included (`reqHeaders` in its `lib/requestOptions.js`), and the shared stage's decorator only re-sets casing ([`createUpstreamProxy`](../../router/upstream.mts)). `Authorization` is therefore whatever `req.headers` holds when the stage runs: set to the minted token ([`applyAuthorization`](router.mts)), deleted (`stripInboundAuthorization`), or left as received. The strip works because [`forwardWithoutInjection`](router.mts) edits `req.headers` before the stage — see the comment above it.
- Logs: the per-request `incoming request` line (`x-request-id`, `method`, `path`; no `event` key) and `injection.*` events carrying the request id and bounded classes only (see [Invariants](#invariants)).

## Invariants

1. **Parsed once.** `req.headers.cookie` is parsed once, at the top of [`injectionMiddleware`](router.mts); every later step reads `extraction.kind` / `.value` / `.skipped`. On the exchange path `Authorization` is handed over once and parsed once, by [`parseBearerAssertion`](bearer-assertion.mts) inside [`createExchangeHandler`](exchange.mts); later steps read `parsed.*`. The session path never parses `Authorization`: the exchange dispatch condition, [`forwardWithoutInjection`](router.mts) and [`applyAuthorization`](router.mts) only check presence. The parsers are tested on their own; that each is called once per request is documented, not tested.
2. **Bytes are never logged, only the bounded reason class** — [`CookieRejectReason`](cookie-extractor.mts), [`AssertionRejectReason`](bearer-assertion.mts), a provider `error` only after [`sanitizeErrorCode`](provider-error.mts), an `error_description` only after [`sanitizeErrorDescription`](provider-error.mts); the unverified `iss` is not logged (the `allowedIssuers` prefilter in [`createExchangeHandler`](exchange.mts)). The one exception: an unclassified throw is logged as `error: String(err)` (`injection.unexpected_error`, `injection.exchange_unexpected_error`), whatever that error's message holds. Pinned by [`never carries the value bytes in the result`](__tests__/cookie-extractor.test.mts), [`neither logs nor returns a session cookie the provider echoes in error_description`](__tests__/router.test.mts), [`forwards a grammar-rejected session cookie anonymously and logs injection.cookie_rejected at warn (#23, #73)`](__tests__/router.test.mts), [`uses the first well-formed same-name pair and logs the skipped malformed one (#74)`](__tests__/router.test.mts), [`does not log a credential a provider echoes back as its error code`](__tests__/exchange-router.test.mts), [`never logs the assertion, the issued token or the client secret`](__tests__/exchange-router.test.mts), [`never puts the assertion or the client secret into an error message`](__tests__/jwt-bearer-client.test.mts), [`drops a provider error_description that is not a safe RFC 6749 description`](__tests__/session-grant-client.test.mts).
3. **The cache is written only on success.** The only `set` calls sit inside the flight after the client returned — the grant fetcher in [`injectionMiddleware`](router.mts) and the exchange fetcher in [`createExchangeHandler`](exchange.mts); no `catch` writes. A provider call happens only when `get` returned `null`, and [`TokenCache.get`](token-cache.mts) evicts an expired entry on read, so a provider error has no live entry to touch. Failures are not cached: [`does not cache a failure: the next identical request is submitted again`](__tests__/exchange-router.test.mts); on the session path this follows from the same structure — documented, not tested at router level.
4. **Expiry is anchored at the request instant.** `requestedAt` is captured before the call goes out (in both fetchers) and the entry expires at `min(requestedAt + ttl, requestedAt + expires_in, exp) − safetyMargin`, where `exp` is the assertion's absolute expiry and exists on the exchange path only (the session path passes no `notAfter`); the entry is not written when that instant is already past. Pinned by [`anchors ttl and expires_in at the request, not at the response`](__tests__/cache-expiry.test.mts), [`keeps an absolute notAfter where it is, however slow the response`](__tests__/cache-expiry.test.mts), [`returns null (do not cache) when the expiry is not after now`](__tests__/cache-expiry.test.mts), [`counts the grant's expires_in from the request, not from a slow response`](__tests__/router.test.mts), [`does not cache a grant whose response arrives after expires_in minus the margin`](__tests__/router.test.mts), [`counts expires_in from the request, not from a slow response`](__tests__/exchange-router.test.mts), [`does not cache at all when the response arrives after expires_in minus the margin`](__tests__/exchange-router.test.mts), [`never outlives the assertion's exp`](__tests__/exchange-router.test.mts), [`does not cache when the assertion has no exp`](__tests__/exchange-router.test.mts).
5. **One flight per key; the rejection is shared; the slot clears in `finally`** ([`SingleFlight.run`](single-flight.mts)). Keys: SHA-256 of the cookie value ([`sha256Hex`](router.mts)); [`exchangeCacheKey`](exchange.mts) for the exchange. The exchange has its own cache and flight table (created inside [`createExchangeHandler`](exchange.mts)), so a cookie whose value equals an assertion never hits the other cache. Pinned by [`invokes fetcher once for concurrent run() on the same key`](__tests__/single-flight.test.mts), [`propagates rejection to all concurrent waiters on the same key`](__tests__/single-flight.test.mts), [`clears pending entry after success`](__tests__/single-flight.test.mts), [`clears pending entry after failure`](__tests__/single-flight.test.mts), [`coalesces concurrent requests with the same cookie into one provider call`](__tests__/router.test.mts), [`submits an assertion once for concurrent identical requests`](__tests__/exchange-router.test.mts), [`shares a refusal with every concurrent identical request instead of resubmitting`](__tests__/exchange-router.test.mts), [`does not share entries with the session cache`](__tests__/exchange-router.test.mts), and the [`exchangeCacheKey` tests](__tests__/exchange.test.mts).
6. **Cancellation is the timeout only.** Neither client accepts a signal; the sole abort is `AbortSignal.timeout(cfg.timeoutMs)` in [`createSessionGrantClient`](session-grant-client.mts) and [`createJwtBearerClient`](jwt-bearer-client.mts). A caller that disconnects does not abort a flight other waiters share: the flight completes, a successful grant is cached and served to the waiters. Documented, not tested. #95 lists changing this as a separate decision (F10).
7. **No retry, no fallback.** One submission per call (the doc comment on [`createJwtBearerClient`](jwt-bearer-client.mts)); the exchange never falls back to the session grant nor the reverse (the `credential_ambiguous` refusal in [`createExchangeHandler`](exchange.mts); [`provider refusals — no pass-through, no session fallback`](__tests__/exchange-router.test.mts), [`rejects a session cookie together with an Authorization header (400), calling nothing`](__tests__/exchange-router.test.mts)). The jwt-bearer client does not follow redirects (`redirect: "manual"` in [`createJwtBearerClient`](jwt-bearer-client.mts); [`does not follow redirects`](__tests__/jwt-bearer-client.test.mts)); the session grant client sets no `redirect` option, so `fetch`'s default (`redirect: "follow"`) applies — nor does validation's `introspect` — unstated in the contract; documented, not tested (F8).

## Failure and lifecycle

- **Timeout / network:** `provider_unavailable` 502 (the `fetch` `catch` in each client); [`throws provider_unavailable on timeout (AbortError)`](__tests__/session-grant-client.test.mts), [`maps a timeout to provider_unavailable`](__tests__/jwt-bearer-client.test.mts), [`answers 502 provider_unavailable on a network error or timeout`](__tests__/exchange-router.test.mts).
- **Provider answers:** the two error-code types say what each status and `error` becomes; the provider's own 401 is `provider_config_error` for the exchange ([`JwtBearerErrorCode`](jwt-bearer-client.mts)) and `session_unauthorized` for the session grant ([`SessionGrantErrorCode`](session-grant-client.mts)), because there the session cookie *is* the credential.
- **State and lifetime (F21):** the session cache and flight table live in the [`createRouter`](router.mts) closure, the exchange's in the [`createExchangeHandler`](exchange.mts) closure — created once per router, which [`app.mts`](../../app.mts) creates once, and held until process exit. There is no dispose: [`TokenCache.clear()` / `size()`](token-cache.mts) are unreachable from outside, and [`app.mts`](../../app.mts) passes no `cleanup` to the shutdown, so a drain does not wipe the caches. Nothing needs releasing — no timers, no held sockets; tokens die with the process ([Threat model — process memory](../../../README.md#threat-model--process-memory)). Documented, not tested.
